Runtime Governance Methodology

运行时治理方法论 · v0.1 Draft · 从真实实现中反向提炼

这是什么

Runtime Governance Methodology 是在智能体的「意图」与它「实际造成的后果」之间建立的一层可被事后独立重放的约束：它要求每个动作在发生前被判定、判定结果不可被推翻或泛化、动作与判定都成为不可改写的事实，并且这一切能够仅凭这些事实被重新推出与证明。

管什么

只治「意图 → 行为」的交界。刻意不治理：智能体的推理内容 · 普通文本输出 · 工具的内部业务逻辑 · 已产生且无法安全回滚的副作用。

为什么需要

普通系统的权限判断是"代码里的一个分支"：它对，你永远不会注意它；它错，你只会在后果里看到它。判断过程本身不留痕、不可回放、不可核验。由此产生三类失效：

  • 无法回答"为什么" —— 某件事发生了，但没有任何记录说明它为什么被允许。
  • 无法证明"没有" —— 系统声称拦住了，但"拦住"与"没执行"都无法被证明。
  • 无法追责分叉 —— 记录说发生了什么，真实世界发生了另一件事，而且没人能发现这个分叉。

核心思想

把判断变成事实

让判定、授权、执行结果都成为不可改写、可被独立重放的记录。

Governance Boundary — 治理边界

治理作用域上界是"意图被固定为事实的那一刻"，下界是"后果成为事实的那一刻"。越过上文是思考，越过下文是不可逆的现实。

治理什么

治理项为什么在边界内
会改变外部状态的动作它是唯一可能造成不可逆后果的东西
与动作相关的授权授权若不能被追溯，"谁同意的"就无从回答
判定判定若不成事实，"为什么允许"就无法回答
事实没有唯一事实，上面三项都失去依托
证明没有可核验的证明，事实只是系统自述
审计没有只读重放，前五项在重启后即失效

有意不治理

不治理项理由（这是设计选择，不是缺陷）
智能体的推理内容治理管的是"做了没有"，不是"想了什么"。管想法既不可行，也无必要
普通文本输出不改变外部状态，不产生需要挽回的后果
工具的内部业务逻辑治理判定"准不准做"，不判定"做得对不对"
已产生且无法安全回滚的副作用已经发生的现实无法撤销。方法论的选择是如实标注，而不假装回滚
为什么"不假装回滚"是一条设计原则："假装回滚"比"承认无法回滚"更危险 —— 后者只是能力缺失，前者会让审计与真实世界分叉。

负空间是方法论的一部分

负空间（当前没有治理的范围）不是附录，它与能力清单同等重要：

  1. 一份只展示"管了什么"的地图，必然被读成"万能治理系统"——这是误导，不是不完整；
  2. 边界的选择本身是方法论内容——"有意不治理推理内容"是一条设计决定，不是遗漏；
  3. 未被治理的区域是可被攻击面——不知道它存在的人，无法评估它。
Source: §2.1 · §2.2 · §2.3 · §2.4

与普通 Agent Demo 的根本区别

维度普通 Agent Demo本方法论要求的
治理结论的性质一次性——运行时的判断，跑完就没了可被反证——每条治理性质都必须能被主动破坏并观察其失效
事实的地位日志是"运行结果的存档"，用于事后翻看事实是唯一被信任的状态，其余一切由它派生、可整体丢弃重建
审计的姿态订阅实时事件、累积内存索引只读重放——不订阅、不留状态，重启后仍须可用
证明的形态没有证明；或复制一份完整记录证明只含引用与哈希，可完全重建，篡改必败
绕过的处理依赖"大家都走这条路"的约定用结构约束保证"不存在第二条路"，并可静态证明
能力清单有测试 = 已覆盖有测试 ≠ 已证明——判据是"破坏它，检查是否必然失败"

Governance Principles — 四条核心原则

四条原则互不重叠，各有独立的失败模式与独立的证明方式。原则层不描述动作，也不含任何实现信息。

P1 · 决定的能力与执行的能力必须分离

约束什么做出判定的实体，不得同时持有执行能力；执行必须汇聚到唯一边界
为什么必须有判定与执行若同体，判定天然可以给自己开例外。更关键的是——只有判定者不持有执行能力时，"不存在绕过"才可能被静态证明。否则你永远无法证明一个有绕过能力的组件不会绕过
违反后会发生什么①判定者自我豁免；②安全强度退化为最松的一环；③"无绕过"从可证明退化为不可证明；④判定可被自己的执行推翻，单调性失去意义
如何证明对判定层做结构扫描（解析代码结构，而非文本搜索）：断言其不存在执行 / 放行 / 覆盖类接口，且其决策过程不产生 I/O 与等待
Source: §3

P2 · 系统只承认一份事实；事实先于动作，且只可追加

约束什么事实的唯一性（无第二真源）、时序（意图先于动作写入）、可变性（只可追加，无改写接口）、可弃性（一切派生可整体丢弃重建）
为什么必须有这是"可审计 / 可回放 / 可恢复 / 可对账"四件事的物理前提。同时它也是"证明只能引用、不能复制"的根据——既然只有一份事实，复制它就会产生第二份
违反后会发生什么①模块自留一份记忆 ⇒ 系统所见与事实不一致，且分叉是静默的、不报错的；②崩溃恢复后两套事实互不相认；③审计结论不可信；④派生视图无法重建
如何证明①物理层面断言"追加不改动既有内容"；②静态扫描"除唯一写入口外无第二条写历史的路径"；③丢弃全部派生、仅由事实重建，结果必须逐条一致；④终态之后任何写入必须被拒
Source: §3

P3 · 治理判定有约束力：否定不可撤销，肯定不可泛化，不确定默认否定

约束什么判定结果的效力范围与时效：
· 否定不可撤销 —— 已生效的拒绝不可被任何后续授权（包括人的即时批准）推翻
· 肯定不可泛化 —— 一次批准只对"这次动作、这些参数、这个主体"有效，不可转移、不可复用
· 不确定默认否定 —— 系统给不出结论时，答案是否定
为什么必须有若否定可被推翻，"拦截"只是建议；若肯定可泛化，"同意"与"行为"脱钩；若不确定默认放行，缺件会静默变成授权
违反后会发生什么①一次人类点击即可撤销规则层的安全判断；②批准 A 却执行 B；③接线缺失时静默放行；④拒绝之后仍然执行 ⇒ 日志说拒绝，现实已改变
如何证明①构造"先拒绝、后批准"的场景，结果必须仍为拒绝；②断言不存在移除 / 重排 / 翻回类接口；③构造"批准参数 ≠ 执行参数"的负例，必须被拒；④覆盖全部拒绝来源，断言执行侧调用计数为零且无配对结果事实；⑤未接线的执行路径必须被拒而非放行
Source: §3

P4 · 结论不得自证：可信度必须来自可重放的事实

约束什么消费者侧纪律：审计不得订阅实时流、不得留状态、不得臆造缺失；证明不得复制事实内容，只能引用；一切结论必须能仅凭事实源重新推出
为什么必须有有了唯一事实源还不够：一个有状态的审计器重启后结论就变了；一个会复制内容的证明就成了第二真源；一个会猜的审计器本身不可信。三者都会让"事实唯一"在实际使用中失效
违反后会发生什么①审计重启后不可用；②证明与事实漂移，"哪一个才算数"失效；③缺失环节被填补成看起来完整的结论；④篡改不可检测；⑤系统退化为"自己说自己没问题"
如何证明①断言审计调用前后事实条数不变（零写）；②断言同一事实源产生相同审计结果；③断言证明的持久化形态只含引用与哈希；④逐字段注入篡改必须使核验失败；⑤缺失必须显式登记，不得填默认值
Source: §3

原则小结

原则一句话独立的失败模式
P1判定者不能动手自我豁免 / 不可证明
P2只有一份事实，且先写意图静默分叉 / 不可回放
P3否定是终局，肯定很窄，不确定就是不行拦截失效 / 授权外溢 / 静默放行
P4可信度来自事实，不来自组件自述审计失效 / 证明漂移 / 篡改不可检测

Governance Capability — 七项治理能力

每项描述的是"系统因此获得的一个可迁移能力"——换一个运行时仍然说得通。

G1 · 执行前判定

获得什么能力
系统能在动作真正生效之前，对该次动作形成并记录一次判断
防什么风险
危险动作绕开全部检查直接生效；事后只能看到结果，看不到判断
属于哪个原则
P1（判定存在）· P3（判定有效力）
一般机制形状
在唯一执行边界之前插入判定；判定取值封闭且互斥；逐条评估、首个非允许即短路；每次判定恰产生一条可追溯的判定记录
方法论边界
只覆盖动作；智能体的推理与文本不经此判定
Source: §4

G2 · 判定与执行的能力隔离

获得什么能力
系统能够静态地主张"不存在绕过判定的执行路径"
防什么风险
判定者给自己开例外；"无绕过"只能靠约定，无法被证明
属于哪个原则
P1
一般机制形状
判定层无执行 / 放行 / 覆盖类接口；越权访问直接失败；依赖方向单向；执行权唯一归属唯一入口
方法论边界
隔离的是能力；判定层仍然写事实——那是它的输出面，不是违规
Source: §4

G3 · 判定不可撤销

获得什么能力
系统能够保证"一旦说了不行，就是不行"——包括对人类后续批准也不让步
防什么风险
存在任一翻回点 ⇒ 安全强度等于最松的一环；缺件时静默放行
属于哪个原则
P3
一般机制形状
禁 API 表 + 越权属性访问直接失败 + 评估短路 + 前序否定传染；接线缺失一律拒绝
方法论边界
传染针对"同一动作的前序判定"，不是全局历史；不构成跨会话的策略记忆
Source: §4

G4 · 授权窄化

获得什么能力
系统能把"同意"精确绑定到"这一次、这些参数、这个主体"，使其不可转移
防什么风险
批准 A 却执行 B（篡改 / 复用）；一次点击成为万能钥匙；身份冒充
属于哪个原则
P3
一般机制形状
批准 ≠ 放行：批准之后重新判定；授权绑定到参数指纹并逐次比对；主体由系统派生，拒不采信外部自报
方法论边界
绑定指纹的具体算法属实现选择；跨会话的信任复用属另一条路径
Source: §4

G5 · 单一事实源

获得什么能力
系统能在任何时刻宣称"我看到的与记录的是同一件事"，并允许派生状态被整体丢弃重建
防什么风险
出现第二份记忆 ⇒ 系统所见与事实分叉，且分叉静默发生；日志只能追认、不能预告意图
属于哪个原则
P2
一般机制形状
意图先于动作落盘；不提供任何改写接口；派生缓存随写入失效、可整体重建；终态后拒写
方法论边界
静态写路径扫描存在已知漏报面（间接写盘形式）
Source: §4

G6 · 只读重放审计

获得什么能力
系统能在不依赖任何内存状态的前提下，事后还原因果、列举拒绝、发现缺口
防什么风险
审计重启后失效；审计器臆造缺失；已跳过的环节永远不被发现
属于哪个原则
P4
一般机制形状
每次调用即时全量重放；不订阅实时流、不留状态；缺失显式登记；固定检查项发现"跳过的环节"
方法论边界
全量重放复杂度随事实量增长；其中一类检查（缓存陈旧）可能尚未实现
Source: §4

G7 · 引用式证明

获得什么能力
系统能产出可离线核验、且不构成第二事实源的证明
防什么风险
证明成为第二真源（与事实漂移）；证明衰减（重放后结论变化）；篡改不可检测
属于哪个原则
P4（根据在 P2）
一般机制形状
证明的持久化形态恰为若干引用字段 + 内容哈希 + 前序哈希链；可由事实完全重建；核验失败即拒
方法论边界
哈希链只能证明"内容自生成以来未被改"，不证明生成时内容本身为真——后者依赖事实层
Source: §4

能力与原则的对应

原则支撑的能力
P1G1 执行前判定 · G2 判定与执行隔离
P2G5 单一事实源
P3G3 判定不可撤销 · G4 授权窄化
P4G6 只读重放审计 · G7 引用式证明
P1 的成对性：只有 G1 而无 G2，判定者可以自我豁免。二者必须同时成立，缺一即 P1 不成立。

各能力的证据要求见下方「Evidence Model」；参考实现的实际证据属另一层内容，不在本页呈现。

Principle → Capability → Mechanism → Evidence

四层抽象结构：越上越稳定，越下越可替换。

┌─ Principle（原则）──────────────────────────────────────────┐
│  = 什么必须成立                                               │
│  换一个运行时仍然成立；不含任何实现信息                         │
└───────────────────────────┬─────────────────────────────────┘
                            │ 每条原则至少支撑一项能力
                            ▼
┌─ Capability（能力）─────────────────────────────────────────┐
│  = 系统因此获得什么能力                                        │
│  可迁移；描述"做得到什么"，不描述"怎么做"                       │
└───────────────────────────┬─────────────────────────────────┘
                            │ 每项能力由若干机制模式兑现（机制可替换）
                            ▼
┌─ Mechanism Pattern（机制模式）──────────────────────────────┐
│  = 通常怎么实现                                                │
│  可替换、可优化；允许出现组件名与具体做法                       │
└───────────────────────────┬─────────────────────────────────┘
                            │ 每种机制必须有能证伪它的证据
                            ▼
┌─ Evidence（证据）───────────────────────────────────────────┐
│  = 凭什么相信它成立                                            │
│  证据强度是它的属性，不是能力的属性                             │
└────────────────────────────────────────────────────────────┘

四条层级纪律

  1. 文件名 / 函数名 / 组件名 / 错误码 / 参数值 —— 只允许出现在 Mechanism 与 Evidence 两层，永不进入 Principle 与 Capability。
  2. 编号永远是 Evidence，不是 Capability。把编号当能力名，等于让某个项目的编号体系冒充通用概念。
  3. "证据强度"是 Evidence 的属性，不是能力清单上的一列标签。同一能力的证据强度可以随验证进展而变化。
  4. Principle 不描述动作；Capability 不描述实现。
Source: §5.1 · §5.2

Governance Lifecycle — 治理生命周期

主执行路径（5 阶段）

① 意图固化
   动作尚未发生，先成为事实。
   · 保留"原始参数"与"校验后参数"两份
   · 【P2】意图必须先于动作写入

        ▼
② 治理判定
   封闭取值（允许 / 拒绝 / 请示）；逐条评估，首个非允许即短路。
   · 若为"拒绝" ⇒ 立即、持久地成为事实，路径在此终止
   · 【P1】判定不得触发任何 I/O 与执行

        ▼
③ 人类裁决与再授权
   仅当判定为"请示"时进入。
   · 发出请求（请求本身成为事实）
   · 等待裁决：批准 / 拒绝 / 超时
   · 若批准 ⇒ 重新判定（等待期间策略可能已变）
   · 并核对：批准时的参数与主体，是否与此刻完全一致
   【P3】批准 ≠ 放行

        ▼
④ 唯一执行边界
   只有通过以上全部，才允许执行。此处是系统内唯一的执行权所在。
   【P1】判定者不在此处

        ▼
⑤ 结果固化
   成功 / 失败 / 被中断，全部如实成为事实。
   【P2】已发生的副作用如实标注，不假装回滚

审计旁路（Audit Path）

从事实源出发（只读）
   ├─ ① 按关联标识还原因果链：请求 → 依据 → 判定 → 审批 → 证明 → 执行
   ├─ ② 列出全部被拒动作，并指出每一条到底有没有执行
   └─ ③ 对账：找出"跳过的环节"

纪律：【P4】零写 · 不订阅 · 不留状态 · 重启后仍可用 · 缺失显式登记

验证旁路（Verification Path）

离线执行，不跑在运行时
   ├─ 逐条追问："若这条性质被破坏，对应的检查是否必然失败？"
   ├─ 找到破坏手段 ⇒ 必须变红 ⇒ 立即还原 ⇒ 确认无残留
   ├─ 结构性判据还要自证："这个判据真能识别违约吗？"
   └─ 找不到破坏手段的性质，降级为"设计意图"，不计入已验证能力

纪律：不做"不自然的破坏实验"；确因代价过高而不做时，书面说明理由

三条路径的关系

路径位置是否在主链上产出
主执行路径意图 → 判定 → 裁决 → 执行 → 结果✅ 是事实
审计路径从事实出发❌ 旁路因果还原 · 拒绝清单 · 缺口清单
验证路径离线❌ 不在运行时反证证据 · 判据自检证据
三条路径互不嵌套：审计不写任何东西，验证不跑在运行时。把二者画进主执行流水线，是这类方法论最常见的表达错误。
Source: §6.1 · §6.2 · §6.3 · §6.4

Abstract Action Example — 抽象动作案例

说明性叙事 · 不是治理能力的证据

本案例完全框架无关：它不使用任何具体实现的名称、路径或编号。真正的证据模型见下方「Evidence Model」。其中每一个动作都能回指本方法论已有的概念。

案例的抽象动作

action( resource, mode )

    resource : 某个受治理的资源
    mode     : 动作模式（可能具有不可逆后果）

系统假设：所有会改变外部状态的动作，都汇聚到唯一的执行边界。

共同前缀（三条路径共享，只讲一次）

① 意图固化

动作尚未发生，请求先成为事实——同时记录原始意图与校验后的参数。

【P2】意图必须先于动作写入。

② 治理判定

在唯一执行边界之前做出判定。判定取值封闭且互斥；逐条评估，首个非允许即短路。

【P1】判定不得触发任何 I/O 与执行。

三条路径

路径 A · ALLOW（允许）
  • ② 判定为允许
  • ④ 抵达唯一执行边界（系统内唯一的执行权所在）
  • 执行
  • ⑤ 结果固化（成功 / 失败，如实成为事实）

事后如何被还原：只读重放按关联标识串起三段 —— 意图 → 判定 → 结果。三段俱全，即为一次完整且可解释的执行。

路径 B · DENY（拒绝）
  • ② 判定为拒绝
  • 拒绝立即、持久地成为事实
  • 路径在此终止
  • 不进入唯一执行边界
  • 不产生结果事实

"拒绝后没有执行"如何被证明

不能只依赖一条"未执行"的日志自述。一句自述本身无法被核验——它只是另一句话，与它所要证明的事情处在同一层信任上。

前提（必须同时成立，正文已各自给出保证）
① 事实完整性成立← §3 P2
② 唯一执行边界成立← §3 P1
③ 执行侧调用计数为零← §3 P3④

在前述前提均成立时，审计通过只读重放检查两件事：

有拒绝事实，且没有与本次动作关联的结果事实⇒ 可判断该动作未执行
有拒绝事实，且同时存在与本次动作关联的结果事实⇒ 结构性矛盾 —— 二者不可能同时成立，说明系统出现严重故障

本口径与 §3 P3 的"如何证明"④（覆盖全部拒绝来源，断言执行侧调用计数为零且无配对结果事实）完全一致；此处不放宽任何条件。

审计结论的依据是"缺失"本身：拒绝之所以能被判断为未执行，不是靠系统声称"我没做"，而是靠该有的结果事实不存在。这也意味着审计不需要信任任何组件，只需要读事实。

【P3】否定不可撤销：已生效的拒绝不可被任何后续授权推翻。

路径 C · REQUIRE HUMAN（需要人工裁决）批准 ≠ 放行
  • ② 判定为"请示"
  • 请求本身成为事实
  • 等待人类裁决：批准 / 拒绝 / 超时（三者均成为事实）
  • 若批准 ⇒ 重新判定（等待期间条件可能已经变化）
  • 并核对：批准所针对的参数与主体，是否与此刻完全一致
  • 只有全部通过，才允许进入唯一执行边界

批准不等于放行。批准只表示"人同意过这一次"，它不构成通行证。系统在批准之后重新走一遍判定，原因有二：

  1. 条件可能已经改变 —— 等待裁决的这段时间里，权限状态可能已经被收紧；
  2. 同意可能被挪用 —— 若批准所针对的参数与此刻要执行的参数不一致，那么这次批准针对的是另一件事。
两种作废情形
✗ 重新判定为拒绝 ⇒ 原批准作废
✗ 批准参数 ≠ 当前执行参数 ⇒ 不允许执行

【P3】肯定不可泛化：一次批准只对"这次动作、这些参数、这个主体"有效。

三条路径统一进入：Read-only Replay（只读重放）

事后，审计只读事实，用同一套还原方法读出三条路径：

路径只读重放读出的序列
Allow意图 → 判定 → 结果
Deny意图 → 拒绝 → 缺少结果
Require Human请求 → 人类裁决 → 第二次判定 → 结果

审计不订阅任何实时流、不留任何状态、不修改任何事实；它只做一件事：把事实串起来，并指出缺失。

再次强调：以上是说明性叙事，不是治理能力的证据。它不构成"该能力已被证明"的依据——证据模型见下方「Evidence Model」。
Source: §6.5

Minimum Viable Governance — 最小可行治理

从零开始建立第一版运行时治理，最少需要 6 步。

顺序纪律（极重要）：步骤 1~3 必须先于任何治理代码的实施。常见错误是先写机制、后补语义定义——这会直接导致大量语义漂移与编号冲突，需要专门的事后清理，成本远高于前置设计。
#步骤输入做什么输出完成判据阶段

2定判定契约 治理范围 定义封闭取值 + 判定者 + "不确定"时的默认值 判定契约 每个取值都有明确后果；不存在未定义分支；"系统不知道时"的答案为否定 Design
3分能力边界 判定契约 确保判定者不持有执行能力；确定唯一执行归属与只读者 能力边界 能静态证明"判定者无法执行" Design

6建立只读审计与反证 运行中的事实源 ①只读还原因果与缺口；②逐条问"破坏该性质，检查是否必然失败" 审计视图 + 反证证据 每项能力都至少有一条"去掉它就必然失败"的检查 Verification

阶段步骤特征

步骤常见失败

Evidence Model — 证据模型

本页只呈现通用的证据模型；参考实现的实际证据属另一层内容，不在本页呈现。

七级证据

层级名称性质强度
E1编号化用例每条治理性质有专属编号；失败时能指出违反哪一条性质最强
E2行为 / 集成验证走真实装配而非替身；替身只用于注入边界强
E3结构扫描用于"不存在某能力"这类无法用行为穷举的断言；必须解析结构，不能文本搜索强（限结构性断言）
E4Mutation（反证）主动破坏该性质，证明检查必然失败；破坏须最小且真实强（证明判据有鉴别力）
E5判据自检对判据本身做测试，排除"判据写错但全绿"强（防最隐蔽的假绿）
E6文档证据有描述、有理由，但未经独立复跑弱
E7编号锚点缺失行为有覆盖，但没有专属编号 ⇒ 只能降级判定不可单独支撑"已证明"

为什么"有测试"不等于"治理能力已经被证明"

功能测试回答的问题是："功能对不对？" —— 它验证的是行为的结果。
治理能力需要回答的问题是："结构上有没有可能绕过？" —— 它验证的是性质的成立。

两者不可互换，原因有三：

  1. 绕过路径无法被穷举。行为测试只能覆盖你想到的路径；"不存在第二条路径"是一个全称命题，只能用结构扫描或等价手段主张。
  2. 判据本身可能是错的。一条断言可以永远为真——不是因为它守护的性质成立，而是因为它写错了。功能测试无法发现这一点。
  3. "测试通过"与"测试有鉴别力"是两件事。一条永远不会失败的检查，与没有检查，在证据意义上是等价的。

核心判据

"如果这条性质被破坏，对应的检查是否必然失败？"

这条判据是可操作的，因为它把"有没有测试"这个无法回答的问题，替换成了一个可以动手做的事：去破坏它，看它会不会红。

由此产生三类诚实结论：

  • covered —— 能构造最小破坏，且检查必然失败；
  • partial —— 只能覆盖该性质的一部分形式（例如只覆盖一类写入路径，另一类未覆盖）；
  • deferred —— 当前不可达或代价过高，书面说明理由（不以凑数代替）。

Capability → 可接受证据类型

本表回答的问题是："该能力原则上可以由哪些证据类型支撑？"
本表不回答："当前某个实现实际拥有哪些证据"——那是「Reference Implementation → 当前实际证据」的问题。两表回答的不是同一个问题，不可互相替代，也不可混读。
能力可接受证据类型（原则上允许）
G1 执行前判定E1 · E2 · E4
G2 能力隔离E3（首选，结构性断言） · E1 · E4
G3 判定不可撤销E1 · E2 · E3 · E4
G4 授权窄化E1 · E2（含负例） · E4
G5 单一事实源E1 · E2 · E3 · E5
G6 只读重放审计E1 · E2
G7 引用式证明E1 · E2 · E3 · E4
降级规则（仅在判定"已证明"时适用）

判定一律以参考实现的实际证据为准。若某能力的实际证据中缺少 E1，即使行为已有覆盖，也只能判为"文档 + 代码证据"，不得计入"已证明"。

注意区分两种"缺 E1"：

  • 可接受类型中不含 E1 —— 说明该能力原则上无法由编号化用例支撑（本版无此类能力）；
  • 实际证据中缺 E1 —— 说明该能力可以由编号化用例支撑，但当前尚未写出该用例。

降级只针对后者。前者是能力属性，后者是进度问题——二者绝不可混为一谈。

What We Do Not Govern — 治理负空间

负空间与方法论正文同等级。本节不是附录，也不是"已知问题清单"——它是治理边界的一部分。

五类负空间

类别含义是否可消除
A · 有意不治理经过判断后决定不管的范围✗ 不消除 —— 它是设计选择
B · 当前缺口应当治理但尚未治理，或治理不完整✓ 可消除（需排期）
C · 实现债务 / 漂移已声明要治理，但实现与声明不一致✓ 可消除（需修复或改声明）
D · 证据不足能力存在，但证据不足以宣称已证明✓ 可消除（需补证据）
E · 尚未开始计划内但完全未开始的面✓ 可消除（需排期）

通用形态（脱离任何具体实现）

A · 有意不治理

推理内容 · 文本输出 · 工具业务逻辑 · 已发生且不可回滚的副作用

B · 当前缺口

非主链路的模型调用不受资源闸 · 某条授权路径不产生凭证 · 某类一致性检查未实现

C · 实现债务 / 漂移

声明要求"统一经某通道"，实现却有第二条落点 · 声明存在某入口，实际为零调用点 · 静态扫描存在已知漏报面

D · 证据不足

某性质只有行为覆盖、无编号锚点 · 某类回归未复跑 · 方法论自身的提炼者与被提炼对象同源，不构成独立验证

E · 尚未开始

计划内的不变量族未开始 · 端到端验收面未形成 · 安全测试面未形成 · 追溯矩阵未开始

为什么不治理

  1. 一份只展示"管了什么"的地图，必然被读成"万能治理系统" —— 这是误导，不是不完整；
  2. 边界的选择本身是方法论内容 —— "有意不治理推理内容"是一条设计决定，不是遗漏；
  3. 未被治理的区域是可被攻击面 —— 不知道它存在的人，无法评估它。

呈现纪律

  1. 必须与能力清单同级呈现 —— 不得折叠、不得移入附录、不得只在末尾一句带过。
  2. 必须分类 —— "有意不管"与"还没管"是完全不同的东西，混在一起会让两者都失去意义。
  3. 必须标注可否消除 —— 否则读者无法判断哪些是设计、哪些是欠债。
  4. 能力声明必须携带其负空间 —— 单独的能力声明是半个结论。

当前明确不能声称的事项

不能声称理由
❌ "完整治理体系已经证明"编号化面仅约半数；端到端与安全证据面尚未形成
❌ "原则自洽 = 实现合规"存在实现与裁定不一致（C 类）
❌ "能力清单 = 覆盖清单"存在真实开放缺口（B 类）
❌ "方法论经过独立验证"提炼者与被提炼对象同源
❌ "遵循本方法论即获得安全保证"本方法论只描述可判定、可留痕、可证明的治理形态，不构成安全保证

边界声明（一句话）

这套方法论只负责"动作发生前后的事实与判定"——它不负责智能体怎么想、不负责工具的业务逻辑对不对、也不负责任何已经发生而无法回滚的后果。

参考实现（某个具体系统）当前具体的缺口、债务与证据状态，属「Reference Implementation」层内容，不在本页呈现。

Governance Methodology Layers — 七层结构

这是 Methodology Layer（方法论层），不是 Runtime Module（运行时模块）。层与代码模块不是一一对应：一个模块可以横跨多层，一层也可以由多处机制共同兑现。层的划分依据是"回答什么问题"，不是"代码放在哪里"。

为什么是这七层

  1. 每层必须回答一个其他层无法回答的问题。凡"可由其他层的输出推导得出"的，不单独设层。
  2. 每层必须产出可被消费的对象。若某层不产出任何被消费的对象，它就不是层，而是属性或活动。

再压缩会丢失语义——例如合并 L4 与 L5 会掩盖"产生治理事实"与"承载治理事实"的区别。再扩展则会产生空层——只描述实现方式、不回答新问题的层，属于机制模式，不配为层。

Layer Overview

治理设计（离线 · 不写代码 · 必须先于实施）
L1治理哪里？不管哪里？
L2谁判定？判什么值？不确定时怎么办？
L3谁能动手？谁只能看？
运行时实施（主执行路径）
L4什么算事实？何时写？可否改？
L5动作如何被拦住或放行？授权如何不外溢？
审计旁路
L6事后如何仅凭事实还原？= Audit Path
验证旁路（离线）
L7凭什么相信防线是真的？= Verification Path
L6 与 L7 不属于同一条执行流水线。它们与前五层不是"先后"关系，而是"依赖"关系：L6 依赖 L4 产出的事实，L7 依赖 L1~L5 产出的防线定义。把二者画进主链，是本领域最常见的表达错误。

Expandable Detail — 每层的七个字段

L1 · 治理边界 — 治哪里 / 不管哪里

干什么找出所有会改变外部状态的动作，确认它们的唯一汇聚点；同时写下刻意不管什么
输入会改变外部状态的动作清单 + 系统架构
输出① 必须受治理的动作类别集合；② 负空间中"有意不治理"的部分
关键约束只治"意图 → 行为"的交界，不治想法；负空间必须与范围同时产出
完成判据能列出全部会改变外部状态的动作类别且指向同一汇聚点；能说出至少一类刻意不管的东西
常见失败模式范围膨胀到推理内容；漏掉非工具型的外部副作用；只写"管什么"、不写"不管什么"
Source: §12.4
L2 · 判定契约 — 判什么值 / 谁判 / 不确定时怎么办
是什么一份语义契约：判定由谁做、取什么值、给不出结论时怎么办
干什么定义封闭且互斥的判定取值、判定者的资格、以及"不确定"时的默认答案
输入L1 的动作类别集合 + 静默风险目录
输出判定契约
关键约束取值必须封闭（不存在未定义分支）；默认答案必须是否定
完成判据每个取值都有明确后果；能明确回答"系统不知道时会怎样"，且答案为否定
常见失败模式取值可扩展 ⇒ 出现绕过用的隐含值；默认值未定义 ⇒ 缺件时静默放行；把"判得好不好"写进契约
Source: §12.5
L3 · 能力边界 — 谁能动手 / 谁只读
是什么一份权力分配：谁可以动手、谁只能看
干什么确保判定者不持有执行能力；确定唯一的执行归属；定义只读者
输入L2 判定契约
输出能力边界（执行权归属 + 只读者定义）
关键约束判定层不得存在执行 / 放行 / 覆盖类接口
完成判据能静态证明"判定者无法执行"
常见失败模式判定层顺手提供"便捷放行"接口；执行权分散在多处；只做文档声明、未做结构约束
Source: §12.6
L4 · 事实层 — 什么算事实 / 何时写 / 可否改
是什么运行时的权威状态载体
干什么定义事实如何产生、如何保存、如何派生——接收写入、规定写入时序、提供只读视图、允许派生被整体丢弃重建
输入L5 提交的写入
输出事实流（唯一 · 只追加）+ 可由事实完整重建的派生视图
关键约束意图先于动作写入；只可追加、无改写接口；派生一律可弃
完成判据所有权威结论都能仅由事实重推；不存在第二条写历史的路径；重建后逐条一致
常见失败模式出现"修正方法"（改写历史）；某处自留缓存并当权威用；写入无统一入口 ⇒ 绕过路径静默存在
Source: §12.7
L5 · 执行闸层 — 如何拦住或放行 / 授权如何不外溢
是什么唯一能够阻止副作用发生的地方，也是唯一持有执行权的地方
干什么在唯一执行边界之前实施 L2 的判定；短路；把否定立即持久化；必要时征求外部裁决并重新判定；把授权绑定到具体动作、参数与主体；通过后才执行；结果如实提交
输入L1 范围 + L2 契约 + L3 边界 + L4 的写入通道
输出本层产生并写入 L4 的治理事实——判定事实、授权事实、执行结果事实。
L4 是这些事实的权威载体；L5 不自行保存副本。
关键约束唯一入口；否定不可撤销；肯定不可泛化；不确定即否定
完成判据被拒的动作确实没有执行，且这件事可查；批准所针对的参数与实际执行不一致时被拒
常见失败模式判定通过后仍留有旁路执行；把外部批准当作放行；授权绑定到"某类动作"而非"这一次调用"；副作用已发生却假装回滚
L4 与 L5 的关系（一句话）：L5 产生治理事实，L4 承载治理事实。二者职责不重叠——L5 回答"准不准、做没做"，L4 回答"记了什么、能不能重建"。
Source: §12.8
L6 · 审计层（旁路） = Audit Path
是什么从事实出发构建的纯派生视图
干什么消费事实，但不修改事实——按关联标识还原因果链；列出全部被拒动作并指出是否执行；以固定检查项发现"跳过的环节"
输入L4 的事实（只读）
输出因果还原 · 拒绝清单 · 缺口清单
关键约束零写；不订阅实时流；不留状态；缺失显式登记、绝不臆造
完成判据调用前后事实条数不变；同一事实源产生相同结果；重启后仍可得出同一结论
常见失败模式依赖实时订阅 ⇒ 重启后失效；缺失被填默认值 ⇒ 审计本身不可信；审计过程顺手写了一条记录 ⇒ 不再是只读
Source: §12.9
L7 · 验证层（离线） = Verification Path
是什么一次离线检验活动，不跑在运行时
干什么逐条追问"若这条性质被破坏，对应的检查是否必然失败"；对结构性判据自证"它真能识别违约吗"
输入L1~L5 的防线定义与验证对象——不消费运行时事实
输出反证证据 · 判据自检证据
关键约束破坏必须最小且真实；验证后立即还原；找不到破坏手段的性质降级为"设计意图"
完成判据每项能力都至少有一条"去掉它就必然失败"的检查
常见失败模式用"有测试"代替"破坏必失败"；为凑数构造不自然的破坏；验证跑在运行时 ⇒ 污染事实
Source: §12.10

可视化设计要点

  1. 纵向表达"从划界到可信结论"的时间轴，不是模块依赖图 —— 最上是尚未运行的设计决定，最下是事后的可信度声明。
  2. 审计与验证必须画在主链之外 —— 审计不在主链上、验证不在运行时；画进主线是这类图最常见的错误。
  3. 必须有负空间带，且与能力同级 —— 一张只展示"管了什么"的地图，会被读成万能治理系统。
  4. 证据强度应按层标注（实测 / 文档+代码 / 编号缺失 / 未验证）—— 让"哪里已经证明、哪里只是声明"一眼可辨。
  5. 证明带应画成横切带，不是一层 —— 它不产生流水线阶段，只约束"事实被引用时的形态"。
  6. 设计段与运行时段应视觉分区 —— 二者的产物、失败模式、完成判据完全不同。
